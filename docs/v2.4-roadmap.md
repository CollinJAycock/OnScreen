# v2.4 Release Roadmap

Next minor release after v2.3.0 (tagged 2026-05-22).

**Lock status: lifted after v2.3.0** (see [server-lock.md](server-lock.md)).
The v2.2.0→v2.3.0 lock did its job; v2.4 may make **coordinated
breaking changes** where they buy real value, as long as the
first-party clients move in lockstep. The default posture is still
"prefer additive" — but v2.4 deliberately takes one breaking change
(the asset-token migration, Track C below: the server stops honoring a
general access token in `?token=`).

**Why this roadmap reads like the v2.3 one.** v2.3.0 didn't ship the
two tracks the [v2.3 roadmap](v2.3-roadmap.md) committed (ABR ladder +
2FA/TOTP). A real-hardware transcode-testing campaign in May
preempted them: validating every encoder family (NVENC / QSV / native
VAAPI / AMF, plus the HEVC + AV1 variants) on actual Intel Arc and AMD
RDNA4 silicon surfaced a HDR-tonemap-on-VAAPI bug, a
slow-first-segment reaper race, a lazy-reprobe gap, and — separately —
an SSRF hole on the SSO discovery paths and a first-admin creation
race. Fixing those *was* v2.3.0, plus the two new AV1 encoder families
(`av1_vaapi` / `av1_amf`) the same hardware made testable. Good
release; not the planned one. **So ABR and 2FA carry forward and
anchor v2.4** — they're still the two highest-impact server-only items
left, and both are confirmed unbuilt in the tree (no `totp` /
`EXT-X-STREAM-INF` code exists today).

Three tracks are committed. Other candidates remain backlog
([server-lock.md](server-lock.md#v23-candidates-not-yet-committed) has
the standing list).

**TV-client status (snapshot 2026-05-22, unchanged from v2.3 cut).**
Android TV / Google TV is on the Play Store closed-testing track;
Fire TV (same Leanback APK) is live on the Amazon Appstore test
channel; the Android phone build is in Play's first-review queue;
Tizen is hardware-verified on a Samsung QN75Q80B (2022) with the
Samsung Apps Store submission package prepared 2026-05-17. webOS and
Roku are code-complete and awaiting real-device soak. None of the v2.4
server tracks below depend on this work; store-review + hardware-soak
completion is what moves the section-8 client rows from ⚠ to ✅ and is
tracked on the client side, not here.

## Track A — Adaptive bitrate HLS ladder

*(carried over from v2.3 — unbuilt)*

Closes the longest-standing documented trail in the comparison matrix
([§2 transcoding](comparison-matrix.md#2-transcoding): "Adaptive
bitrate ladder (multi-rendition HLS)" is ❌ for OnScreen, ✅ for all
three competitors). OnScreen transcodes a single rendition per session
and lets the operator-side bandwidth profile pick; Plex / Emby /
Jellyfin emit multi-rendition variant playlists so the player switches
on real-time network conditions.

| Item | Complexity | Notes |
|---|---|---|
| Multi-rendition target generation | L | Compute a ladder (e.g. 480p/720p/1080p/2160p) per source resolution; cap at source-resolution height. Surface as a fleet config knob so an operator can pin to a single rendition for cost. |
| Variant playlist (`#EXT-X-STREAM-INF`) emit | M | Update the master m3u8 generator in [`internal/transcode/`](../internal/transcode/) to list each rendition with bandwidth + resolution attributes. Per-rendition media playlists already work; the master playlist is the new piece. |
| Per-rendition ffmpeg session orchestration | M | Currently one ffmpeg per session; ABR needs N parallel ffmpeg invocations sharing the source decode where possible. Hardware-decode-once + multiple software encodes vs. N independent decodes — benchmark on real content, now that we have validated NVENC / QSV / VAAPI hosts on hand from the v2.3 campaign. |
| Bandwidth-aware client switching | S | HLS players switch on their own when they see a multi-variant master; the web player's hls.js already has ABR logic. Manual override stays in the quality picker. |
| Telemetry | S | Per-session rendition selection over time, exposed in `/api/v1/sessions` + the OTel transcode span attributes so operators can see what bitrate the client actually settled on. |

**Sized total:** ~M+L over the transcode pipeline; rough 2-week cycle.

**API additions:** `features.abr_ladder` capability flag (so older
clients can detect support), per-session `selected_rendition` field on
the session details response. Both additive — v2.2 clients ignore the
new flag/field.

## Track B — 2FA / TOTP

*(carried over from v2.3 — unbuilt)*

Closes a Plex / Emby / Jellyfin parity gap for password-based
accounts. Drops cleanly into the existing PASETO + session shape; no
schema rework, just additive endpoints + a new optional flag on the
local-login flow.

| Item | Complexity | Notes |
|---|---|---|
| `users.totp_secret` column + migration | XS | Encrypted-at-rest column on the existing `users` table. AES-256-GCM via the existing encryptor (same path as `tmdb_api_key` etc.). Additive migration — fits the lock. |
| `/auth/totp/setup` + `/auth/totp/verify` + `/auth/totp/disable` | S | Standard `otpauth://` URI + QR-code payload. Recovery codes printed once, hashed at rest, single-use. |
| Local-login two-step | S | When a user has TOTP enabled, `/auth/login` returns `201` with `totp_required: true` + `login_challenge_token`; client posts the 6-digit code + challenge to `/auth/totp/verify`. Existing PASETO path unchanged. |
| Capabilities flag | XS | `features.totp` so clients can show/hide the "Enable 2FA" toggle. |
| Web + Android-phone client flows | M | Settings → Security → Enable 2FA with QR display, recovery-codes download, disable-with-current-code. TV clients skip the *enable* flow (awkward on a TV) but must handle the *verify* step on login. |
| OIDC / LDAP / SAML interaction | XS | Federated providers ship their own 2FA at the IdP — OnScreen-local TOTP is local-account-only. Document explicitly so admins don't expect it to apply to OIDC users. |

**Sized total:** ~1 week server + ~1 week web/Android-phone client
flows. Server side closes the matrix-parity row immediately;
TV-client verify-on-login is the polish item.

**API additions:** new endpoints under `/auth/totp/*`, new
`features.totp` capability flag, new optional `totp_required` +
`login_challenge_token` fields on the `/auth/login` 201 response.

## Track C — Security & performance hardening follow-ups

The v2.3 security pass (OIDC/SAML SSRF, first-admin advisory lock,
artwork redirect cap) shipped the high-severity findings and deferred
three lower-severity items. With the lock lifted, item 1 takes the
full (breaking) shape rather than the additive half-measure.

| Item | Complexity | Notes |
|---|---|---|
| Purpose-scope asset tokens + close the URL-token leak | M | A new `purpose=asset` token (24 h, user-scoped, no Bearer replay) is minted at login/refresh/PIN-switch. The asset middleware (`RequiredAllowQueryToken`) now accepts only `stream`/`asset` tokens in `?token=` and **hard-rejects the general access token** — closing the leak where a general-API credential rode in a URL (logs / Referer / history). **Breaking** for cross-origin clients (browsers use the cookie and are unaffected); all six client surfaces migrate to the asset token in lockstep. Two pre-existing route-grouping gaps surfaced and are flagged for a follow-up: `/items/{id}/image` (photos) and `/api/v1/tv/channels/{id}/stream.m3u8` (Live TV) sit under `Required`, so they need moving under `RequiredAllowQueryToken` for cross-origin players that can't send a header. |
| Nonce-based CSP (`script-src`) | M | Per-request nonce replaces `'unsafe-inline'` on `script-src`; the Go server stamps the matching nonce onto the SPA shell's two inline `<script>` tags at serve time (shell served `no-store` so the nonce can't be cached stale). `style-src` **keeps** `'unsafe-inline'` — the SPA renders dynamic inline `style=""` pervasively, which nonces can't cover; refactoring every dynamic style to CSS custom properties is out of scope and far lower XSS value. Needs a browser soak (zero CSP violations on load) before ship. |
| FK indexes on `watch_events.media_id` + `media_items.parent_id` | XS | Additive migration (`00002`). The cascade RI lookups seq-scanned these — the existing `idx_watch_events_user_media` composite can't serve a `media_id`-only equality, and `idx_media_items_parent` is partial (`WHERE deleted_at IS NULL`), unusable by the cascade. The v2.2 bulk-delete hang on QA was the symptom. Both indexed (non-partial), validated on real Postgres. |

**Sized total:** ~1 week (the client fan-out for the asset token + the
nonce-CSP browser soak dominate; the FK indexes are an afternoon).

**API additions:** new optional `asset_token` field on the auth
response. The CSP change is observable only as a stricter response
header; the `?token=` hard-reject is the one breaking change.

## Not committed for v2.4 (still backlog)

See [server-lock.md](server-lock.md#v23-candidates-not-yet-committed).
Ship in a v2.4.x dot release or fold into v2.4 if a track finishes
early.

- **Last.fm / ListenBrainz scrobble exporter** — ~1 week. Listen
  events already live in `watch_events`; a one-way exporter closes the
  named [§6](comparison-matrix.md#6-playback--client-ux) trail
  ("Last.fm / ListenBrainz scrobbling", ❌ vs community plugins on the
  others). Strong candidate to fold into v2.4 if Track C lands fast.
- **Audio loudnorm filter** — ~3 days, music polish. ffmpeg one-pass
  loudnorm behind a per-session "Normalize" toggle.
- **`jellyfin-ffmpeg` base image pin — re-evaluate, likely drop.**
  This was parked "until the Intel Arc test box arrives." That blocker
  is now cleared — the v2.3 campaign validated native `*_vaapi` on
  both Intel iHD (Arc A770) and AMD radeonsi (RDNA4) using the
  **distro** ffmpeg, and it came out 2–5× faster than QSV on HDR
  sources. The custom Hable curve `jellyfin-ffmpeg` carries targets
  the OpenCL/zscale path; our validated VAAPI path already emits
  correct `bt709` tonemap. The original value proposition has mostly
  evaporated. Recommend formally retiring this candidate unless a
  specific tonemap-quality regression surfaces on a customer GPU.

## Anti-goals (not v2.4, possibly never)

- **DLNA / UPnP** — permanently scoped out
  ([matrix](comparison-matrix.md#deferred--workaround-in-place)).
- **SyncPlay / watch parties** — permanently scoped out.
- **Trailers / extras** — value-vs-effort doesn't pay back.
- **Tauri desktop picture-in-picture** — webview doesn't expose
  `requestPictureInPicture` on Windows; not worth a custom miniplayer.
- **Forking ffmpeg from scratch** — too expensive to maintain; the
  `jellyfin-ffmpeg` pin above was the productive shape of that idea
  and is now itself recommended for retirement.
- **ML personalised recs / pgvector** — item-to-item CF shipped and
  was pulled; no renewed demand signal.

## What v2.4 closes in the matrix

If all three committed tracks land:

- §2 — **Adaptive bitrate ladder** flips ❌ → ✅ (Track A).
- §7 — **2FA / TOTP** becomes a new core row, ✅ where competitors
  need plugins (Jellyfin) or a paid tier (Emby SAML-adjacent) (Track B).
- §10 — **Strict CSP** tightens (nonce-based) and the token surface
  narrows (Track C).
- §11-adjacent — the FK-index work removes the bulk-delete hang
  documented during v2.2 QA (Track C).

The comparison matrix header still reads "Snapshot … against v2.2.0";
re-snapshot it to v2.3.0 (AV1 rows already updated) as a housekeeping
pass, and again at the v2.4 cut.
