# v2.3 Release Roadmap

Next minor release after the v2.2.0 server lock (see
[server-lock.md](server-lock.md) for the lock posture). v2.3 is
additive only — new endpoints, new fields, new capability flags;
nothing in the v2.2.0 contract gets removed or renamed.

Two tracks are **committed** as of 2026-05-10. Other v2.3+ candidates
remain backlog ([server-lock.md](server-lock.md#v23-candidates-not-yet-committed)
has the full list).

**TV-client status (snapshot 2026-05-12).** Parallel to the v2.3
server work, the Tizen client hardened to hardware-verified on a
Samsung QN75Q80B (2022) between 2026-05-11 and 2026-05-12 —
sideloaded via partner cert, with the full surface exercised end-
to-end (navigation, video / audio / music / photo playback, watch
state, library hygiene). webOS is at near-parity in code, awaiting
real-LG soak. The v2.3 server tracks below ship independent of this
work; both should land in the same window.

## Track A — Adaptive bitrate HLS ladder

Closes the longest-standing documented trail in the comparison matrix.
OnScreen currently transcodes a single rendition per session and lets
the operator-side bandwidth profile pick; Plex / Emby / Jellyfin emit
multi-rendition variant playlists so the player can switch on real-time
network conditions.

| Item | Complexity | Notes |
|---|---|---|
| Multi-rendition target generation | L | Compute a ladder (e.g. 480p/720p/1080p/2160p) per source resolution; cap at source-resolution height. Surface as a fleet config knob so an operator can pin to a single rendition for cost. |
| Variant playlist (`#EXT-X-STREAM-INF`) emit | M | Update the master m3u8 generator in `internal/transcode/` to list each rendition with bandwidth + resolution attributes. Per-rendition media playlists already work; the master playlist is the new piece. |
| Per-rendition ffmpeg session orchestration | M | Currently one ffmpeg per session; ABR needs N parallel ffmpeg invocations sharing the source decode where possible. Look at hardware-decode-once + multiple software encodes vs. N independent decodes; benchmark on real content. |
| Bandwidth-aware client switching | S | HLS players switch on their own when they see a multi-variant master; OnScreen's web player uses hls.js which has ABR logic. Manual override stays in the quality picker. |
| Telemetry | S | Per-session rendition selection over time, exposed in `/api/v1/sessions` + the OTel transcode span attributes so operators can see "what bitrate did the client actually settle on for this user." |

**Sized total:** ~M+L over the transcode pipeline; rough 2-week cycle.

**API additions:** `features.abr_ladder` capability flag (so older
clients can detect support), per-session `selected_rendition` field
on the session details response.

## Track B — 2FA / TOTP

Closes a Plex / Emby / Jellyfin parity gap for password-based
accounts. Drops cleanly into the existing PASETO + session shape;
no schema rework, just additive endpoints + a new optional flag on
the local-login flow.

| Item | Complexity | Notes |
|---|---|---|
| `users.totp_secret` column + migration | XS | Encrypted-at-rest column on the existing `users` table. AES-256-GCM via the existing encryptor (same path as `tmdb_api_key` etc.). |
| `/auth/totp/setup` + `/auth/totp/verify` + `/auth/totp/disable` endpoints | S | Standard otpauth:// URI + QR-code payload. Recovery codes printed once, hashed at rest, single-use. |
| Local-login two-step | S | When a user has TOTP enabled, `/auth/login` returns `201 with totp_required: true + login_challenge_token`; client posts the 6-digit code + challenge to `/auth/totp/verify`. Existing PASETO path is unchanged. |
| Capabilities flag | XS | `features.totp` so clients can show/hide the "Enable 2FA" toggle in the user settings UI. |
| Web + Android phone client flows | M | Settings → Security → Enable 2FA flow with QR display, recovery-codes download, disable-with-current-code. The TV clients can skip the *enable* flow (it's awkward on a TV) but must handle the *verify* step on login. |
| OIDC / LDAP / SAML interaction | XS | Federated auth providers already ship their own 2FA at the IdP — OnScreen-local TOTP is local-account-only. Document this explicitly so admins don't expect it to apply to OIDC users. |

**Sized total:** ~1 week server + ~1 week web/Android-phone client
flows. Server side closes the matrix-parity row immediately;
TV-client verify-on-login is the polish item.

**API additions:** new endpoints under `/auth/totp/*`, new
`features.totp` capability flag, new optional `totp_required +
login_challenge_token` fields on the `/auth/login` 201 response.

## Not committed for v2.3 (still backlog)

See [server-lock.md](server-lock.md#v23-candidates-not-yet-committed):

- **Last.fm / ListenBrainz scrobble exporter** — ~1 week.
- **Audio loudnorm filter** — ~3 days, music polish.
- **jellyfin-ffmpeg base image pin** — was committed earlier, now
  parked until the Intel Arc test box arrives. Reason: our
  production hardware (RTX 5000) routes HDR tonemap through
  NVENC's CUDA pipeline, *not* the OpenCL / zscale path
  jellyfin-ffmpeg's custom Hable curve targets. Visible gain on
  the current deployment is ~0%. The VAAPI patches are the real
  win and only matter once we have Intel iGPU hardware to validate
  on. Defer.

These ship in v2.3.x dot releases or get folded into v2.3 if the
client cycle leaves slack.

## Anti-goals (not v2.3, possibly never)

- DLNA / UPnP — permanently scoped out
  ([matrix](comparison-matrix.md#deferred--workaround-in-place)).
- SyncPlay / watch parties — permanently scoped out.
- Forking ffmpeg from scratch — too expensive to maintain; the
  `jellyfin-ffmpeg` pin above is the productive shape of that idea.
- ML personalised recs — pulled once, no renewed demand signal.
